- (direction by user) User explicitly rejected a general AI chatbot; wants a Statmuse-style natural-language stats lookup instead (look up specific stats on players/teams/dates and other factors).
- (decision by user) New, separate page/section for the search UI (not merged into the existing Explorer page).
- (decision) Support both team-level and player-level queries; player-level answers were expected to stay empty until real player data landed.
- (event) Data blocker resolved: nba_api historical backfill landed real player_game_stats rows (699 rows, spot-checked correct), unblocking player-level queries.
- (decision) Reject RAG/embeddings for this feature: the data is small, well-typed Postgres tables with exact values, so a SQL/tool lookup gives deterministic correct answers; vector similarity would trade that for lossy, hallucination-prone retrieval with no accuracy benefit.
- (decision) Use tool-calling (function-calling): the LLM is given a small fixed set of typed query tools and must call them and report literal results, rather than freely generating facts.
- (decision) Architecture: a Next.js BFF route (e.g. app/api/search/route.ts) runs the agentic tool-use loop and holds the LLM API key server-side (same secret-handling pattern as API_SERVICE_KEY today); the tool implementations are new read-only FastAPI endpoints querying Gold tables via the existing api_reader role. Rejected a standalone assistant microservice (extra deployable/operational surface not yet justified).
- (decision) LLM: Claude Haiku 4.5 (cheap, fast, well-suited to extraction/classification workloads).
- (capability) CAP-1 Natural-language player/team stats query — intent: a user asks a specific stats question in plain English (e.g. player points on a given date, a team's result in a game) and gets a correct answer without knowing the schema; success: the answer matches the ground-truth row in games/player_game_stats for in-range questions.
- (capability) CAP-2 League leaders / aggregate query — intent: a user asks a leaderboard-style question (e.g. who leads in assists) and gets a ranked answer computed from real ingested data; success: every aggregate answer explicitly discloses the date range/game count it was computed over, never a bare number.
- (capability) CAP-3 Head-to-head / game-result query — intent: a user asks about the outcome or stat line of a specific game between two teams; success: the tool returns the correct game row and the model reports it verbatim with a citation.
- (capability) CAP-4 Transparent sourcing on every answer — intent: every answer states which table and date range it came from; success: a user (or reviewer) can trace any returned number back to a specific query tool call and its literal result.
- (capability) CAP-5 Honest gap/ambiguity handling — intent: when a question has no matching data or an ambiguous subject (e.g. two players with a similar name), the system says so instead of guessing; success: a zero-row tool result produces an explicit 'no data' response, and an ambiguous name produces a clarifying list of candidates, in both cases never a fabricated number.
- (constraint) v1 tool set is fixed and narrow (player stats, team games, leaders, game result) — no general/arbitrary SQL-execution tool, to avoid injection/data-exposure risk and keep the least-privilege security model intact.
- (constraint) Stateless per question for v1 — no persisted multi-turn conversation history/session model.
- (constraint) New FastAPI tool endpoints must carry the same slowapi rate limiting as existing routes and must run under the api_reader role (read-only, least-privilege, same as every other api/ route).
- (constraint) Testing must follow this repo's existing offline-verification convention: FastAPI tool endpoints tested against fake rows (no live DB), BFF tool-use loop tested with the Anthropic SDK call mocked (no real LLM calls in CI).
- (constraint) Feature branches off main, not off the in-progress v2-sportsbook-redesign branch, so the two ship as independently reviewable PRs.
- (non-goal) No voice interface.
- (non-goal) No predictive/generative stat projections (e.g. win-probability) — that's the PRD's own already-deferred stretch goal under a different name.
- (non-goal) No fine-tuning a model on this data — tool-calling against live Postgres already gives exact, current answers.
- (non-goal) No general sports-knowledge chatbot (trivia, historical stats outside this pipeline's own ingested data, opinions) — scope stays 'assistant for this pipeline's real data,' not a wrapper around the model's general knowledge.
- (non-goal) Data-quality-observatory NL narration (why did source X and Y disagree, schema drift explanations) is a related but separate feature, not in this spec's scope — offered to the user as an alternative direction and not selected this round.
